## Pipeline (all under ~/capture/listmonk on the VM)
1. `python3 seed.py init`, then `docker compose -p rea-listmonk -f compose.yml up -d`; the install, upgrade check and
   server start take under a second after Postgres is healthy. The healthcheck uses `/health`: in v6 `/api/health` needs a
   session (403 "invalid session"), which kept the first container in `starting`.
2. `python3 seed.py`: logs in through the `/admin/login` form (fields `username`, `password`; the `nonce` field only matters
   for OIDC), keeps the `session` cookie for this script, and through `/api/`:
   - removes the install-time samples (lists "Default list" and "Opt-in list", subscribers john@ and anon@ example.com,
     the "Test campaign", and the 4 sample templates after making "Tide Table Letter" the default, since their bodies link
     to the project's website), so every object in the capture is synthetic;
   - creates, idempotently by name: 4 lists, 6 subscribers with JSON attributes (one blocklisted), 3 templates
     (2 campaign, 1 transactional), 3 draft campaigns, 1 user role ("Ledger Auditor"), 1 list role ("Kitchen List
     Editors"), 1 user (ada.finch, no password login), 1 uploaded 64x16 PNG generated with zlib/struct;
   - sets `app.root_url`, `app.site_name`, `app.from_email`, `app.check_updates=false` through
     `PUT /api/settings/{key}` (each triggers an in-process reload; the seed waits for `/health`), and names the admin
     profile "Rea Admin <rea-admin@example.test>" (the installer sets `rea-admin@listmonk`);
   - logs out. A second run creates nothing. Writes `seed-ids.json` (ids only).
   The first media upload failed with "open uploads/...: no such file or directory": the image has no uploads directory,
   hence the volume.
3. `NODE_PATH=~/capture/node_modules node listmonk/capture.mjs`: login through the form, then the admin pages. The sidebar
   groups are collapsed, so most links are not visible; the capture drives the app's own Vue 2 router
   (`__vue__.$router.push`) and clicks a link only when it is visible. The first attempt fell back to page loads and paid
   8 bootstraps (8 x `/api/config`, `/api/profile`, `/api/lang/en` at 41 KB, `/api/events`); router navigation removed
   them. Scripted fetch sequence (session cookie, no CSRF header needed): lists page + each of the 4 lists by id;
   subscribers page + each of the 6 subscribers by id; data export of 2 subscribers; activity of 2; bounces of 1;
   campaigns (`no_body=true`) + each of the 3 by id; templates (`no_body=true`) + each of the 3 by id; users + ada.finch
   and rea-admin by id; user roles; list roles; media + the PNG by id; bounces; public lists; dashboard counts; about;
   import status; filters `query=subscribers.attribs->>'city' = 'Granite Point'`, `list_id=`,
   `query=subscribers.status = 'blocklisted'`, campaigns `query=granite`, lists `query=depot`; then POST a scratch list,
   PUT it, GET it, DELETE it, GET it again (a missing list is a 400 with a JSON message in listmonk, not a 404), re-read the lists.
   Full HAR 4.5 MB (deleted after scoping).
4. `python3 ~/capture/scope_har.py listmonk.full.har listmonk.scoped.har --origin http://127.0.0.1:3214 --keep-regex '^/api/(?!lang/|events)'`
   -> kept 68 (GET 65, POST 1, PUT 1, DELETE 1; statuses 200 x67, 400 x1); dropped path 45 (admin shell, static, public
   assets, `/api/lang/en`, `/api/events`), non-json 0, auth 2 (GET/POST `/admin/login`), big-body 0, over-max 0.
   134,271 bytes, sha256 `db06948f2b2e2525759589dd9788f84edfa163926ae67c9c4e49c2f3b64962d0`. Credential grep: admin and
   database passwords 0 hits, token shapes 0, `session=`/`nonce=` 0. The only URL in the scoped HAR is the app origin.
5. `python3 ~/showcase/envbuild.py all listmonk` with `exclude_tools`
   `settings|config$|about$|profile$|dashboard|running_stats|import|public_lists|subscribers$`
   (`subscribers$` drops the subscriber list, whose first recorded call is the UI's with seven query parameters, four of
   them empty; the per-id, export, activity and bounces tools stay).
   - capture Evidence `ev_40b38ad41b4906c91a10812bd33a562c757b5bbf249f84f2f5b173e3fe59f0ba` (68 records, observed);
     manifest `ev_2219c491a30c79107897a70884bbe76d8376ccb7f2c67943c7583baeea100cac` (inferred, view digest

## Manifest facts
- 29 tools (GET 26, POST 1, PUT 1, DELETE 1), 11 templated groups, all from the built-in `numeric` rule (listmonk ids
  are integers; UUIDs appear only inside bodies). The opt-in rules matched nothing; the no-rules manifest has the same 29
  tools and 11 numeric parameters (8 limitations instead of 9).
- 24 query-parameter names across tools, 11 distinct (list_id, minimal, no_body, order, order_by, page, per_page, query,
  search, status, subscription_status); 2 tools with a body shape (POST lists, PUT lists/{id}); statuses 200/400;
  0 excluded groups; coverage complete-within-view 29/29; unknowns authorization-model, response-semantics,
  state-transition.
- `DELETE /api/lists/{id}` answers 200 with `{"data": true}`, so it is an ordinary JSON tool.
- UI-only tools besides the scripted ones: config, profile, dashboard charts, campaigns running stats, and the lists call
  with `minimal=true&per_page=all` that every page makes.
- Every listmonk body is wrapped in `{"data": ...}`, so task fields read `data.name`, `data.results[0].name`; the subscriber
  data export is the exception (`profile[0]...`, `subscriptions[...]`).

## Surprises
- v6 moved the unauthenticated health route to `/health`; `/api/health` now requires a session.
- A fresh install ships sample lists, subscribers, a draft "Test campaign" and four templates that link to the project's

- `GET /api/lists/{id}` for a deleted list is a 400, not a 404.
